# ULTIMATE Vibe-coder guidebook [BETA]

A learning portal written for the author's brother: 22 learning chapters, orientation chapter 00 and a single glossary (394 definitions / 11 topics), 6 Mermaid diagrams. React, TypeScript, Vinext and an npm lockfile; native Sites starter. The learning data is compiled at build time, and the text of the current page is part of the initial HTML. No backend, accounts, analytics or agent runtime have been added.

## Running and checking

Node.js 22.x, at least 22.13 (`engines` `^22.13.0`), and npm (the reference version is in `.nvmrc`, e.g. `nvm use`): `npm ci`, then `npm run dev`. The address is printed in the terminal. Production: `npm run build`, then `npm start`.

- `npm run doctor` — environment check: Node against `engines` and `.nvmrc`, npm, consistency of `package.json` / `package-lock.json` / `node_modules`, the branch and a clean git tree, Chrome for Mermaid. FAIL (exit 1) — an unsuitable Node or `node_modules` does not match the lockfile; WARN — working on `main`, a dirty tree, Node differs from `.nvmrc`, no Chrome while SVGs are reused.
- `npm run validate` — a single entry point for checking the project: `content`, `test`, `typecheck`, `lint`, `build` in sequence; the first FAIL stops the rest (SKIP). Then validate compares `git status` before and after: any new change (stale generated files, new untracked files) is a FAIL, with no exceptions. The `typecheck` cache (`tsconfig.tsbuildinfo`, `incremental: true`) is not tracked by git and is ignored (`*.tsbuildinfo` in `.gitignore`). Exit 0 only on an overall PASS.
- CI (GitHub Actions, `.github/workflows/ci.yml`, check `validate`) — on every pull request with any base and on push to `main`: Node from `.nvmrc`, `npm ci`, `npm run validate`, then `node .github/scripts/check-diagram-assets.mjs` and upload of `dist` as artifact `dist-<SHA>` (14 days). CI has no Chrome: if a diagram is new or changed and its SVG is not committed, `render-diagrams` writes `error` to the manifest, and CI fails on the SVG check (or on the `tree` step). Render the diagram locally with Chrome and commit `public/diagrams/*.svg` and `src/content/diagram-assets.json`. Workflow permissions are `contents: read`, no secrets are used; a new push to a PR cancels the outdated run, runs on `main` are not cancelled. Changing a PR's base without a push does not restart CI: after a retarget a push is needed (for example, merging the new base into the branch).
- CI, check `e2e` — after `validate` in the same run: `npm ci`, downloads artifact `dist-<SHA>` (the same `dist`, no second build), installs Playwright Chromium (`npx playwright install --with-deps --no-shell chromium`), starts `npm start` in the background and waits for `http://127.0.0.1:8787/` to respond (up to 90 s), then `npm run test:e2e -- --forbid-only --add-reporter=html`. Any failed test makes the check red. Artifact `e2e-report-<SHA>` (14 days, uploaded on failure too): the HTML report `playwright-report/` (`npx playwright show-report playwright-report`), `docs/browser-results.json`, traces of failed tests in `.sites-runtime/playwright/` (open with `npx playwright show-trace <trace.zip>`) and the server log `e2e-server.log`. The browser in CI is `HANDBOOK_BROWSER_CHANNEL=chromium`: Chromium of the revision pinned by `@playwright/test` in the lockfile, in new headless mode; locally the default is still Microsoft Edge. Browsers are not cached: according to the Playwright documentation, restoring the cache takes as long as downloading, and Linux system dependencies (`--with-deps`) are not cached; only npm is cached (`setup-node`). Timing (measured 2026-10-22, `ubuntu-24.04`): a green e2e job ≈ 3.5 min — `npm ci` ≈ 30 s, installing Chromium with dependencies 19–87 s, tests ≈ 1 min; a test failing on timeout adds up to 60 s; job timeout 30 min. `e2e` starts after `validate` (≈ 1 min 45 s). If `validate` failed, `e2e` is skipped.

- `npm run content` — AST/GFM, HTML allowlist, glossary/search/anchors, independent coverage audit.
- `npm test` — content/download parity, original SHA256, inventory, targets, sanitization, appendix rejection, longest-match and preview threshold.
- `npm run typecheck` and `npm run lint`.
- `npm run test:e2e` — Playwright / the installed Microsoft Edge. Needs a running server; `HANDBOOK_URL` sets a different address (default localhost:3000; `npm start` listens on `http://127.0.0.1:8787`). `HANDBOOK_BROWSER_CHANNEL` sets a different Playwright channel (`chromium` in CI).
- `npm run build` — production Worker build and an automatic `postbuild` audit of public/dist for private provenance and the implementation appendix.

PowerShell for the current dev port: `$env:HANDBOOK_URL='http://127.0.0.1:5173'`, then `npm run test:e2e`.

## Content

Edit `content/handbook.md`: it is the source of the learning content, the definitions and the downloadable Markdown. The "Overview" layer of chapters with tabs is `content/overview/NN.md` (see the section "Tabs and the "Overview" layer" below). The parent sources are kept unchanged; their SHA256 hashes are in `docs/original-source-hashes.json`. After the agreed editorial cleanup, the learning source intentionally differs from the original document.

Compilation outputs: `src/content/generated.json`, `public/handbook.md`, `docs/coverage-report.json`. The downloadable Markdown matches the learning source exactly. Home page `/`, chapters `/chapters/01`–`/chapters/22`, glossary `/glossary`, all material expanded at `/print`.

Tool overviews: `/tools`, `/tools/codex`, `/tools/claude-code`. They are written in the same `content/handbook.md` and included in search, Markdown and print, but do not change the route or the progress of the 22 chapters. The subscription matrices and feature availability were checked on 2026-10-11 against official sources; research notes: `docs/codex-research.md` and `docs/claude-code-research.md`. When updating, check each client's documentation, releases, price and limits separately, then change the visible check date.

Mark supplementary material with paired HTML comments `<!-- details: Title -->` and `<!-- /details -->` (the text after `details:` becomes the visible summary title). The compiler first marks up and indexes individual blocks, then wraps them in `<details>`: search and canonical anchors keep working inside closed blocks. Keep mandatory steps and warnings outside.

The glossary registry is extracted from chapter 23. Definitions of up to 160 visible characters that consist of one plain paragraph get a tooltip; short definitions with an official link get a non-modal popover, long/structured ones get a panel. Services, local tools and libraries are labeled explicitly; links open in a new tab. The name and aliases are not counted. All current definitions are short; the long branch is checked by a separate browser fixture without changing the production text.

Autolinks are kept for all matching occurrences. Word forms and ambiguities: `src/content/term-overrides.mjs`. The compatibility registry `block-identities.json` keeps the IDs of unchanged blocks, `practice-identities.json` keeps the old checklist keys. New blocks get a separate namespace. After editing, check overrides, targets and **0 unexplained gaps**. Coverage includes the dynamic evidence/owner panels and definition previews, with recursive markup explicitly excluded. Raw executable source is protected; Copy returns the source from the registry.

## URL map

The new structure (P2-05, plan RD-01, ADR-0003): 9 rail sections — Home `/`, Start `/start`, Basics `/base`, Flow `/flow`, Control `/control`, Reliability `/reliability`, Practice `/practice`, Tools `/tools`, Agent Pack `/agents`; outside the rail — Reference `/reference` (cheatsheet 22, glossary). A chapter is `/<section>/<NN-slug>`; its 4 tabs are path segments, not a query: Overview is the chapter address itself, How it works `/how-it-works`, How to apply `/apply`, Check yourself `/check` (for example `/flow/08-preflight/apply`).

`src/content/url-map.json` is the machine-readable map, edited by hand (it is not a generated file). A `pages[]` entry: `old` (the current address), `new` (where the content moves), `section`, `chapter` (id from `generated.json`); chapters with tabs also have `tabs: true`, `lead` (the tab for the text before the first subheading) and `anchors`: every subheading and interactive panel of the chapter → a tab. Other anchors (blocks, term occurrences) follow the subheading they sit under; the chapter id belongs to Overview. `keep: true` — the old address stays a live page with different content (`/` → Home, while introductory chapter 00 moves to `/start/00-how-to-read`); `alias: true` — an old address that is not in the build now (`/chapters/23`); `live: true` — the chapter has already moved (P5-02b, currently only 08): its tabs are built at the new addresses (`app/(reader)/flow/[chapter]/…`, component `ChapterTabPage`), the old address is not built and answers 308, and the compiler writes into the anchor registry, links and search the address of the tab that holds the id (the chapter heading belongs to Overview). A page without tabs can also be `live` (P2-05b: glossary → `/reference/glossary`, cheatsheet 22 → `/reference/22-cheatsheet`): its route is `app/(reader)/<new>/page.tsx`, the old address is not built and answers 308, and all its anchors (the glossary's and all `term-*`), links, search and `href` in `generated.json` point to the new address. The interface gets such a page's address from `pageHref(id)` in `src/content/chapter-routes.ts`, not from a string in code. Tab addresses for the chapter template come from `chapterTabHrefs()` in `src/content/chapter-routes.ts`; a chapter in `generated.json` has, next to the old `path`, an `href` — the address for menus and navigation. The Vercel build fails if a chapter is `live` but one of its tabs is not built. Logic: `scripts/url-map.mjs`.

Redirects turn on by themselves as pages move, with no flag: `scripts/vercel-output.mjs` adds a 308 `old → new` (also for the trailing-slash form, in one hop) only for entries whose new page is already in the build; until then the old address answers 200 as before. The Vercel build fails if it contains a page that is not in the map, and if the anchor registry still points to an old address that already redirects in this build (otherwise Reader would send an old link back to the old address, and the 308 back to Overview: a loop). `npm test` (`tests/url-map.test.mjs`) checks: every build route, every static page `app/**/page.tsx` and every chapter is in the map; every subheading and panel of a chapter has a tab, with no extra anchors; all anchors from `generated.json` find their new page; there are no chains, cycles or duplicate addresses; nothing moves to `/` or a section root, service pages (`service`) keep their address; broken entries are caught. `check-vercel-output.mjs` checks every entry over HTTP: a 308 to an existing target, or 200 while there is no target yet. The browser keeps the anchor on the old address after a 308; if it is not on the page, Reader looks it up in the anchor registry (`public/data/anchors-*.json`) and goes to the page given there (`Reader.tsx`, restoring old links). The compiler builds the registry; when a chapter moves (P5), take the anchor path in the registry from the map's `resolveAnchors`, so that an old link leads to the right tab.

How to add or move a page: a new page (including `app/<path>/page.tsx`) needs a `pages[]` entry (for a new address with no past, `old` = `new`; a service page gets `section: "service"`); a new subheading in a chapter with tabs needs a line in its `anchors`, otherwise `npm test` fails; renaming a subheading changes its id — fix the key in `anchors`. When the new page appears in the build, the old address starts redirecting by itself; remove the old route from the build in the same PR, otherwise it is unreachable, and switch the anchor registry to `resolveAnchors`, otherwise the build fails.

## Tabs and the "Overview" layer

Format P5-01 (brief 8.1–8.2). Chapters 01–21 are built as 4 tabs. The compiler (`src/content/compiler.mjs`, option `urlMap`) distributes a chapter's text from `content/handbook.md` across tabs using the same map `src/content/url-map.json`: a block goes to the tab of the `###` subheading it sits under, text before the first subheading goes to the `lead` tab, and the chapter heading goes to `heading` for the hero. Every block lands in exactly one tab, nothing is cut. A `<!-- details: -->` block that spans subheadings of different tabs, and a subheading without a tab in the map, fail the build. In `generated.json` such a chapter has `heading`, `tabs[]` (`id`, `html`, `outline`, `panels`) and `overview`. The chapter's whole `html` stays for the current pages for now. Search entries of chapters with tabs have a `tab` field; search and anchor paths change when the chapter becomes `live` (see "URL map"). In the Overview tab, example code is shown expanded (`.overview-example`) rather than collapsed as in the chapter text.

The Overview layer is the file `content/overview/NN.md` (`NN` is the number of a chapter with tabs). The template is mandatory; the compiler checks every rule and fails with the file name:
- frontmatter: exactly `chapter` (matches `NN`), `title`, `minutes` (integer > 0), `rule_strength` (`MUST`, `SHOULD` or `MAY`), each key once, the value unquoted or in paired double quotes; BOM and CRLF are allowed;
- only `##` sections, exactly these and in this order (the headings are literal tokens the compiler matches, so they stay in the content language): `Зачем` ("Why"), `Правило` ("Rule"; the rule is a single non-empty `>` quote), `Как это выглядит` ("What it looks like"), `Три вещи, которые нужно сделать` ("Three things to do"; only a numbered list of 3 non-empty items), `Частая ошибка` ("Common mistake"), `Проверь себя` ("Check yourself"); an empty section is a FAIL;
- no more than 350 words, 1 table and 1 Mermaid diagram; no HTML and no `<!-- details -->`.

The overview goes through the same pipeline as the chapter text: sanitization, glossary autolinks, code blocks, search (`tab: 'overview'`), coverage audit. Block ids are `ch-NN-overview-*`; they can be linked to (`[Правило](#ch-NN-overview-правило)`, the id is a slug of the heading), and they are not part of the legacy anchor registry `anchors`. The search entry for the chapter heading gets `tab: 'overview'`, as does the chapter id itself in the URL map. The overview comes first in the Overview tab. While the file does not exist, the Overview tab is empty: the texts are written in P5-04 and P6 and accepted by the editor agent (brief 9.5). `docs/coverage-report.json` → `tabs`: the number of chapters with tabs, distributed blocks and overviews. Tests: `tests/content-tabs.test.mjs` (the fixture `tests/fixtures/overview-08.md` is for the test only and does not reach the site).

## Agent Pack

`agent-pack/` is a portable set of the guide's rules for an AI agent in someone else's repository: a normative `AGENTS.md` (roles, lifecycle, gates; every rule links to a chapter), `CLAUDE.md` for Claude Code, and starter `skills/`, `schemas/`, `claude/`. Setup and version: `agent-pack/README.md`. The pack does not change this repository's root `AGENTS.md` / `CLAUDE.md`.

Delivery to the agent (P8-03, brief 11.3) is built as the last step of `npm run content` — `scripts/agent-delivery.mjs`, with no new dependencies:

- `/agents` — the pack page: a "Download Agent Pack (.zip)" button, links to `llms.txt`, the description from `agent-pack/README.md` and the file list. The page data is `src/content/agent-pack.json` (committed, like `generated.json`).
- `/agent-pack.zip` — exactly the files of `agent-pack/` in an `agent-pack/` folder. No compression, paths in alphabetical order, one date for all entries, Unix permissions (hooks are executable): identical files give identical bytes on any machine. The condition is a checkout without line-ending conversion (`core.autocrlf=false`, as in CI and on Vercel): otherwise the file bytes, the sizes in `agent-pack.json` and the executable bit change.
- The Markdown of each page is the page address + `.md` (`/chapters/08.md`, `/tools/codex.md`; the introductory chapter is `/index.md`). The text is cut from `content/handbook.md` by the top-level `##` headings of the CommonMark tree (remark); a heading that is not in `generated.json`, or a chapter appearing twice, is a FAIL. For a live chapter with tabs (P5-02b), its overview from `content/overview/NN.md` comes first, under `### Обзор` (the "Overview" heading), as on the page: no front matter, `##` sections become `####`, `](#anchor)` links point to the tab that holds the anchor; an anchor that is in no tab is a FAIL. After the overview comes a `---` rule, then the chapter text. Links to the site of the form `](/…)` become absolute. The file is also written at the old address from the URL map, so that links from the pack survive the page moves (P5).
- `/llms.txt` — a map for LLMs in the [llmstxt.org](https://llmstxt.org) format (checked 2026-10-27): H1, a summary quote (the opening quote of `content/handbook.md`), link lists by rail section, with the glossary and materials under `## Optional`. `/llms-full.txt` — the same header and the whole `content/handbook.md`. Links are absolute and point to production (`SITE_ORIGIN` in the script; changes together with the domain, P4-05).
- The "Copy for agent" button and the "Page Markdown" link were removed from chapters and overviews by founder decision on 2026-10-29 (P8-05): page Markdown is still built and served at the addresses above, via `/agents` and `llms.txt`; the "Download Markdown" link for the whole guide stays in the menu.

The archive, `llms*.txt` and the pages' `.md` files are build artifacts in `.gitignore`; checks: `tests/agent-delivery.test.mjs` (the archive is byte-for-byte equal to `agent-pack/`, reproducibility, the `llms.txt` format, Markdown for every page) and `tests/browser/agents.spec.ts`.

## Glossary levels

`content/glossary-levels.json` (P6-07) holds the level of every term in section 23: `basic` ("Basic") — general development vocabulary, where the term means the same outside the guide (Git, GitHub, environment, tests, web formats, services); `professional` ("Professional") — terms of the agentic engineering method and the guide's strict formulations, even if the word is known outside it (roles, task states, evidence and checks, risk and security, parallel integration, agent events and control). In `terms`, each topic (`"23.3"`) has two lists of ids; every term is in exactly one list of its topic, otherwise `npm run content` fails with the term's name. `collapsed` — topics and the label of the group into which their basic terms are gathered at the end of the topic (currently Git, `23.3`); navigating to `#term-*`, search, the "Basic" filter and `/print` expand it. The compiler writes `level` into `GlossaryTerm`, `data-level` on the card and a visible level label (`.term-meta`, P6-07b); next to the label, `GlossaryEnhancer` adds a "Copy link to term" button (address `#term-*`, result in `role=status`). The paragraph starting with the bold marker `Служебный формат для сайта:` ("Service format for the site", matched literally by the compiler) at the start of section 23 stays in the Markdown but is hidden on the page and in search (`.glossary-service-note`). Definitions, anchors and search do not depend on the level. A new term in `content/handbook.md` requires an entry in this file. The editor agent checks the classification (brief 9.5). Tests: `tests/glossary-levels.test.mjs`, `tests/browser/glossary-levels.spec.ts`.

`content/gamification/drills/NN-name.json` (P7-03, brief 10.3) is a chapter's drill in the "Check yourself" tab: one file per chapter, 5–8 situations, each with a question, 2–4 options, the correct answer, an explanation, the `anchor` of a chapter paragraph and a difficulty of 1–3. The format is defined by `content/gamification/schema/drill.schema.json`; `npm run content` validates the schema without new dependencies (`src/content/drills.mjs`) and fails with the file name if an id repeats, an answer is not among the options, or an anchor is not from this chapter. The compiler writes `drills` into `generated.json`, and each card gets an `href` to the tab that holds the anchor. The skill counts as passed from 80% correct answers; the best result is stored in ProgressStore (`drills`). Without JavaScript, the tab shows all situations with answers behind a disclosure. The card text is learning content: the editor agent checks it against the chapter (brief 9.5). Tests: `tests/drills.test.mjs`, `tests/browser/drill.spec.ts`.

## Reading and learning

With JavaScript, terms open an explanation in place; without JavaScript they are canonical glossary links. A tooltip does not change scroll, URL or history. The term's tooltip and panel show its level. Long definitions and two templates (chapter 06 / chapter 14) use a non-modal desktop drawer / a modal mobile sheet. An explicit jump to the glossary keeps the exact origin for returning.

Progress is local and lives in a single ProgressStore (`src/components/progress-store.mjs`, P7-01): key `mae-progress`, record `{version: 2, completed, exercises, practice, reading}`. Chapters and the reading position are stored by the stable page and tab ids from `src/content/url-map.json` (`ch-08`, tab `apply`), not by addresses, so moving pages does not lose progress. API: `get()`, `set(update)` (false if storage refused), `subscribe(listener)`, `unavailable()`, `damaged()`. The v1 → v2 migration runs once on the first read: `handbook-learning-v2` (chapters and exercises), `handbook-reading-v2` (last page and scroll), `practice:*` (checklists) and the oldest `handbook-progress` (the chapter opens from the start: the old absolute coordinate does not apply). Each part is read separately, a broken one is skipped, and the interface reports it. The old keys stay in place (a backup in case of a rollback) and are no longer written. Tests: `tests/progress-store.test.mjs` (the fixture `tests/fixtures/progress-v1-main.json` was captured from a real session on `main`) and `tests/browser/progress-migration.spec.ts`. There is explicit resume, undoing completion, four achievements and reset. If localStorage fails, marks are kept in memory across pages until the tab reloads; the interface reports it. If the clipboard fails, the source can be copied manually.

## Speed and learning profile

The shared interface is in `app/(reader)/layout.tsx` and persists across Link navigations. A page passes only its own definitions, outline and example sources through ReaderPageData. Search and compatibility of old anchors are separate `public/data/` files with a hash in the name: search loads when opened, the registry only for an old unresolved link. Search opens with the button at the top of the rail, in the bottom bar, ⌘K / Ctrl+K and "/"; results are grouped (pages, terms with level, cheatsheet, text), and an empty query shows suggestions and recent pages (P3-03, `src/design/search-groups.mjs`, `docs/design/visual-language.md` §12). A pending navigation shows an indicator, and if it lasts longer than 500 ms, a skeleton in place of the page; reduced motion turns off decorative motion. The skeleton is client-side (`Reader`), without `loading.tsx`: such a Suspense boundary moved the page text out of the initial HTML into a hidden block, and without JavaScript only a placeholder was visible (P1-12). Links in the rail, the mega menu and the "Sections" menu (mobile navigation P3-02: the bottom bar and full-screen menu below 1024 px) prefetch the route on intent (hover, focus, touch), not when they appear on screen.

`npm run content` also generates static Mermaid SVGs and lazy assets. An SVG is reused when the source/config hash matches. A new or changed diagram needs Chrome: on Windows the installed Google Chrome is used; configure other environments via `MERMAID_CHROME_PATH`. The browser renderer is not included in the client bundle. An error in an individual diagram expands its text and shows diagnostics. The learning Markdown remains the only source of the diagrams.

The build includes the native Vinext prerender; HTML/RSC artifacts are in `dist/server/prerendered-routes/`. Reader routes use the standard static cache. No manual response cache has been added on top of Sites access control. Prerender Node seeding should not be taken as proof of a cache hit on a cold production Worker: the actual local headers and limitations are recorded in the implementation notes.

The profile computes XP from existing marks: chapter +100, exercise +50, maximum 2450. Four levels, four badges for chapter groups and an optional badge for exercises. Marking again gives no extra points; undoing reduces XP. There are no new accounts, quizzes, penalties for missed days or mandatory tasks.
